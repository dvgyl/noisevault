Real qubits make mistakes

This is IBM Fez, a quantum computer with 156 qubits. Every qubit makes errors at its own rate, and IBM measures those rates in a regular check called a calibration. The rates drift over time, so each calibration gives a new set of numbers.

The 156 qubits of IBM Fez in their chip layout, scaled in both size and colour from 0.15% to 10.6% readout error.

Take one kind of error, the readout error. It is the chance that a measurement gives the wrong bit, and on 26 February 2025 it went from 0.15% to 10.6% across the 156 qubits.

Log-scale dot plot of all 156 IBM Fez qubits sorted by readout error from 0.15% on the left to 10.6% on the right.

Most simulators leave the mistakes out

A simulator calculates what a quantum computer would output. Take a GHZ circuit, which links three qubits so that they always agree when you measure them. An ideal simulator runs it 1,024 times, and every run gives 000 or 111.

A 32 by 32 grid of 1,024 runs on an ideal simulator showing 0 wrong runs.

Now run the same circuit with the IBM Fez profile, and 27 of 1,024 runs come out wrong. A real device gives wrong runs like these, so any work on handling errors needs them in the simulation too.

The same 32 by 32 grid of 1,024 runs with the IBM Fez profile showing 27 wrong runs marked as filled orange squares.

One profile, four simulators

NoiseVault stores the calibration of one device on one date in a single file, called a profile. It builds that profile into the noise model of Qiskit, Cirq, PennyLane or Stim, so the same numbers reach whichever simulator you use. nv check then runs small test circuits through each build and compares the results with an exact calculation.

One IBM Fez profile file connecting to Qiskit, Cirq, PennyLane and Stim, each marked with a pass check mark.

A fingerprint pins the numbers

Every profile has a fingerprint, a code calculated from every number in the profile. Even a tiny change gives a different code. If one gate error of IBM Fez grows by 1%, 116 of the 256 bits change.

A 16 by 16 grid of the 256 fingerprint bits of IBM Fez showing 116 changed bits outlined in orange after a 1% gate error change.

Put the fingerprint in your paper. When a reader loads the profile with it, NoiseVault checks the numbers first and stops with an error if they differ. So a reader either gets exactly your noise or finds out at once.

fez = nv.load("ibm_fez@2025-02-26", expect="...")

The 16 by 16 fingerprint grid beside the pinned nv.load call expecting the IBM Fez fingerprint.

Every build says what it lost

A simulator can't always represent everything that a calibration measures. So instead of approximating in silence, each build writes a report of what it kept exactly, what it approximated and what it left out. Save the report next to your results, and a reader can see what your simulation contained.

Score a profile against a device

A profile is a model of the hardware, so it helps to know how far it is from the real thing. nv compare takes counts measured on a device and fits two factors, one for the gate errors and one for the readout errors. A factor of 1 means the errors in the profile already fit the counts, and each factor comes with a 95% interval.

In this example the counts come from a simulation with known factors, and both intervals contain the true values.

25 devices, ready offline

The package includes 25 devices, 18 from IBM, 5 from Quantinuum and 2 from Google. They load with no network and no account, so a test suite gets the same numbers on every machine. When you need a newer calibration, nv pull gets it from IBM.

What you can do with it

Each of these has a short script in the examples folder, so you can start from working code.

Test error mitigation
Run two error mitigation methods from Mitiq on the noise of IBM Fez, and compare each result with the ideal value.
Compare devices
Run the same GHZ circuit on two IBM and two Quantinuum devices and one hypothetical device, and plot how the success rate falls as the circuit grows.
Train under device noise
Train a small PennyLane circuit on IBM Fez, with gradients that flow through the calibrated noise.
Correct errors in Stim
Run a surface code memory in Stim with calibrated noise, and decode it with PyMatching.
Track drift
Pull the IBM Fez calibrations of today and of 90 days ago, and see what changed.
Design a device
Describe a device that doesn't exist yet, save it as a profile, and run it in Qiskit and Stim.

Get started

  1. 1

    Try it without an install

    With uv, this one command prints the IBM Fez profile.

    $ uvx --from noisevault==__VERSION__ nv show ibm_fez
  2. 2

    Install for your simulator

    Replace qiskit with cirq, pennylane or stim if you use another simulator.

    $ pip install "noisevault[qiskit]==__VERSION__"
  3. 3

    Simulate with real noise

    This is the GHZ circuit from above. It runs offline and prints the counts, with a few wrong runs among them.

    from qiskit import QuantumCircuit, transpile
import noisevault as nv

sim = nv.load("ibm_fez").to_qiskit()

ghz = QuantumCircuit(3)
ghz.h(0)
ghz.cx(0, 1)
ghz.cx(1, 2)
ghz.measure_all()

compiled = transpile(ghz, sim, seed_transpiler=1)
counts = sim.run(compiled, seed_simulator=1).result().get_counts()
print(counts)

What the model leaves out

The models use average error rates and treat every error as independent of the others. As a result, they don't include these five effects.

Crosstalk
An operation on one qubit disturbs its neighbors.
Leakage
A qubit leaves its two working states.
Coherent errors
Small rotation errors add up in a systematic way.
Idle noise
A waiting qubit makes errors, and the model adds them only where the circuit has explicit delays.
Correlated readout
The readout errors of different qubits depend on each other.

No profile has been scored against counts from a real device yet. The limitations page gives the full list.
